# 1단계 보고: 서울 상권 원자료 수집 (2026-11-24)

## 요약
- seoul_commerce 수집기(Open API 방식)는 이 실행 환경에서 쓸 수 없었다. 같은 데이터셋을 **서울 열린데이터광장의 파일·시트 다운로드**로 받았다.
- 7종 중 **6종 확보**, **집객시설(OA-15580) 1종 미확보** (Open API 전용).
- 기간: **2021년 1분기 ~ 2026년 2분기 (22개 분기)**. 설계서 가정(약 21분기, 2026년 1분기까지)보다 1분기 많다.
- 받은 파일을 seoul_commerce 수집기 출력 형식으로 바꿨고, seoul_commerce의 자체 읽기 함수(`preprocessing._read_source_csv`) 형식 검사를 6종 모두 통과했다.

## 4. 형식 변환 (`adapters/opendata_to_contract.py`)
열린데이터광장 파일은 한국어 컬럼명이고, seoul_commerce는 Open API 영문 컬럼명을 기대한다. 변환 스크립트는 **이름만 바꾸고 값은 건드리지 않는다.**
- 결과: `data/raw/contract/*.csv` (용량이 커서 저장소에는 올리지 않음. 스크립트로 30초 안에 다시 생성)
- 연도별 파일과 시트가 겹치는 2025년은 연도별 파일을 쓰고, 시트에서는 2026년 분기만 가져왔다.

### 확인한 사항
| 확인 | 결과 |
|---|---|
| 같은 컬럼이 파일마다 다른 이름 (점포 수) | 2021~24년 파일 `점포_수`·`유사_업종_점포_수`, 2025년 파일 `stor_co`·`similr_induty_stor_co`, 시트 `일반_점포_수`·`전체_점포_수`. 2025년 겹치는 304,775행에서 **값 100% 일치** |
| 전체 점포 수 = 일반 + 프랜차이즈 | 모든 파일에서 100% 성립 → seoul_commerce의 해석(`SIMILR_INDUTY_STOR_CO`=전체)과 일치 |
| 매출: 2025년 파일 대 시트 | 겹치는 85,732행 숫자 값 **모두 일치** (상권 이름 표기만 218행 다름) |
| 매출 시트의 깨진 헤더 | 건수 시간대 열이 `시간대_건수~06_매출_건수` 형태. 금액 열과 같은 순서로 대응 |
| 영역: shapefile 대 seoul_commerce 저장소의 `trade_area.csv` | 1,650개 상권 코드·좌표·면적 **모두 일치**. 상권명 2건(오탈자/표기), 행정동 1건 다름 |
| seoul_commerce 읽기 함수 검사 | 6종 통과. 분석 범위(20211~20261) 필터 후 외식업 기준 점포 258,931행, 매출 142,554행 |

## 5. 설계서와 다른 점
1. **수집 경로**: 수집기 대신 파일·시트 다운로드 + 형식 변환 스크립트. 변환 스크립트는 설계서 3절 대안("파일명과 컬럼은 data_contracts.yml 형식에 맞춘다")을 실행한 것이다.
2. **집객시설 1종 없음** → seoul_commerce 전처리(`run_preprocessing`)는 7종이 모두 있어야 돌아가므로 **그대로는 실행되지 않는다.** (2단계 결정 사항)
3. **기간이 1분기 더 길다**: 2026년 2분기까지 있다. seoul_commerce 설정은 2026년 1분기에서 자른다.
4. **상권 경계(면) 자료가 있다**: 설계서는 "점 좌표만 있다"고 가정했지만 영역-상권 파일은 경계 shapefile이다. geosnap의 `rook`/`queen`(경계 인접) 이웃도 쓸 수 있다.
5. **매출 자료가 없는 상권 52개**: 점포 자료는 1,650개 상권, 매출은 1,598개 상권.
